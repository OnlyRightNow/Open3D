## Motivation and Context

`o3d.t.geometry.AxisAlignedBoundingBox.to(device)` and `.clone()` return a wrong box: a box with min (-3, -3, -3) and max (-1, -1, -1) comes back with max (0, 0, 0) and a warning, and a Float64 box comes back as Float32. A commenter on the issue proposed this exact fix in 2024.

## Description

**Plan summary**
- Goal: `To(device, copy)` and `Clone()` keep min/max bounds, color and dtype.
- Requirements: no spurious "invalid bounding box" warning; result does not alias the source; the `!copy && same device` fast path is unchanged.
- Test method: new C++ test `AxisAlignedBoundingBoxPermuteDevicePairs.CopyDeviceKeepsBounds` (Float32 and Float64, negative bounds), new Python test file, all existing AABB tests, plus the triage repro.
- Risk: Float64 copies now stay Float64 instead of being downcast. That is the documented intent.

**Root cause**
`cpp/open3d/t/geometry/BoundingVolume.cpp`, `AxisAlignedBoundingBox::To` builds a default box (zero bounds, Float32) on the target device and calls `SetMaxBound` then `SetMinBound`. The setters cast to Float32, and `SetMaxBound` validates the new max against the default zero min, so a negative max is rejected.

**Change**
Construct the copy with the existing two-bound constructor, which keeps the dtype, then copy the color.
